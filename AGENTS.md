# AGENTS.md

This repository is a pnpm monorepo for the Infineon Design System.
See `CONTRIBUTING.md` for detailed development workflows and conventions.
Read the sections relevant to the task rather than treating this file as a replacement for it.

## Sources of truth

Work from source files, not generated output.

* Stencil components live under `packages/components/src/components/`.
* Component implementation and JSDoc are the source for generated component API artifacts.
* Storybook stories are also machine-readable inputs used to generate framework examples and MCP example data.
* Shared story parsing and framework code generation lives in `packages/dds-tooling/`.
* Core component behavior belongs in the Stencil components, not in framework wrappers.

When changing an existing pattern, inspect nearby components, but do not assume every legacy API is a preferred precedent.

## Generated files

Do not manually edit generated output when the upstream source can be changed instead.

In particular:

* `packages/components/src/components.d.ts` is generated by Stencil.
* In component `readme.md` files, content below `<!-- Auto Generated Below -->` is generated by Stencil. Content above that marker may be maintained manually.
* `dist/docs.json`, `dist/cem.json`, `dist/`, `loader/`, and `build-wrapper/` contain generated build output.
* `stencil-generated/**` inside framework wrappers is generated from the Stencil build.
* Generated files and regions under `examples/` are produced by the example generator. Preserve manual content outside auto-generated markers.

Wrapper packages also contain intentional hand-written integration code. Do not treat an entire wrapper package as generated.

## Storybook and examples

Storybook stories are not only documentation: they are consumed by tooling to produce HTML, React, Vue, Angular, and MCP examples.

When adding a component that should appear in generated framework examples:

1. Add or update its Storybook story.
2. Register the appropriate story variant in `example-generator/src/index.ts`.
3. Run the example generator.

Do not register every story blindly. Some stories are intentionally excluded because they require browser-only behavior, manual JavaScript, or structures unsupported by the generator.

If generation or story parsing behaves incorrectly across multiple consumers, check `packages/dds-tooling/` before implementing framework-specific fixes.

## Public APIs and framework integration

Treat public props, events, methods, and slots as cross-framework APIs.

Follow the conventions documented in `CONTRIBUTING.md`. Preserve backwards compatibility unless the task explicitly requires an API migration.

When changing value-like or form-related APIs, review `packages/components/stencil.config.ts` for:

* Vue `componentModels`
* Angular `valueAccessorConfigs`
* existing custom Angular value accessors

Do not fix core component behavior by editing generated React, Vue, or Angular wrappers.

If a component has a colocated `*.figma.ts` Code Connect file, check whether public API changes require updating that mapping.

## Accessibility

Prefer native semantic HTML where it provides the required behavior. Use ARIA only where native semantics are insufficient.

Preserve expected keyboard interaction, focus behavior, accessible names, and component semantics when changing interactive components.

Storybook accessibility checks currently surface violations but do not by themselves prove that a component is accessibility-compliant.

## Commands and verification

Use pnpm for repository development.

Useful commands:

```bash
pnpm install
pnpm build:components
pnpm build:wrappers
pnpm test
pnpm test -- <component>.spec.ts
pnpm lint
pnpm check:ci
pnpm generate:examples
pnpm storybook
```

Run the smallest relevant checks while iterating, then validate the surfaces affected by the change.

* Component behavior change: run the affected tests and component build.
* Public API or framework-facing change: also build affected wrappers.
* Story or generator-relevant change: regenerate and verify affected examples.
* Docs-only changes generally do not require the full build/test suite.

Use `pnpm check:ci` for non-mutating repository validation. `pnpm check` runs Biome with `--write` and may modify files.

## Avoid

* Do not edit generated files to work around an upstream source issue.
* Do not duplicate Stencil behavior in framework wrappers.
* Do not manually patch generated examples instead of changing their story or generator source.
* Do not copy a legacy API pattern without checking documented conventions and related components.
* Do not make unrelated refactors as part of a focused change.
* Do not update generated snapshots or artifacts merely to make validation pass without understanding the underlying change.
